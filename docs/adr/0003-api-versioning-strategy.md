# ADR-0003 — API versioning strategy: hard-cut to `/v1/`, OpenAPI as source of truth

- **Status:** Accepted
- **Date:** 2026-07-28
- **Authors:** Michael (Founder), ZeroGEX
- **Related ADRs:** [0001](./0001-recontract-api-for-freshness-and-versioning.md),
  [0002](./0002-canonical-response-envelope.md),
  [0004](./0004-deprecation-policy-and-customer-communication.md)

---

## Context

ADR-0001 committed us to re-contracting the API. ADR-0002 defines the
new shape. This ADR defines *how we version it* — how consumers
discover version, how we introduce breaking changes, how we prevent
accidental ones, and how we prevent the ambiguity Johnnie observed
across three feedback rounds from re-forming under the new contract.

Baseline (per `docs/api-audit/`):

- `FastAPI(version="1.0.0")` is set in `main.py:277` but only surfaces
  in `/openapi.json`. Consumers cannot query it from a stable endpoint.
- One router (`levels.py`) already mounts at `/api/v1/levels/{symbol}`;
  every other router mounts under `/api/`. Mixed convention.
- `API_Guide.md` at line 219 explicitly acknowledges the `/api/v1/levels`
  design: *"the internal `/api/gex/*` models can change without breaking
  integrations."* That precedent implicitly admits the current
  non-`v1` surface is unstable — we've been telling customers the same
  thing.
- OpenAPI schema is auto-generated by FastAPI. There is no hand-authored
  spec, no CI diff check, no capability endpoint, no changelog file.

## Decision

Four coordinated commitments:

1. **Hard-cut to `/v1/` for the entire re-contracted surface.** Every
   market-sensitive endpoint moves to `/v1/`. The current shape lives
   at `/legacy/` for exactly 90 days from launch, then is removed.
2. **OpenAPI 3.1 spec is the source of truth for the API.** It is
   hand-authored, versioned in the repo, and consumed by CI, types,
   docs, and the SDK. FastAPI's auto-generated spec is replaced by a
   spec-first pipeline.
3. **Machine-readable capability and changelog discovery via
   `/v1/version`.** Consumers query one endpoint to learn schema
   version, build, feature flags, and get a pointer to the changelog.
4. **Breaking-change CI gate.** A GitHub Action diffs the OpenAPI spec
   between the base branch and the PR branch. Breaking changes require
   an ADR (or a "breaking-change acknowledged" label) plus a version
   bump per the semver policy below.

The default assumption for any new endpoint is: **it's part of `/v1/`**.
No new endpoints are added outside `/v1/` for any reason after Tier 1
lands.

## The `/v1/` hard-cut

### URL structure

Under v1:

- **`/v1/{domain}/{resource}`** — e.g. `/v1/gex/summary`, `/v1/flow/series`.
- **`/v1/version`** — capability + changelog discovery (see below).
- **`/v1/health`** — liveness (separate from freshness per ADR-0002).
- **`/v1/openapi.json`** and **`/v1/docs`** — the versioned spec and its
  Swagger UI.
- **`/legacy/{path}`** — the pre-v1 shape, unchanged, for 90 days.
  Emits `Deprecation`, `Sunset` headers on every response per ADR-0004.

Everything under `/v1/` is versioned by the URL prefix. Everything under
`/legacy/` is a compat shim that keeps existing integrations working.

Path components use **kebab-case** consistently (fixing the snake-case
outliers `/gex/vol_surface`, `/gex/premium_surface` observed in the
baseline audit — they become `/v1/gex/vol-surface`, `/v1/gex/premium-surface`).

### Response versioning

Every `/v1/` response carries an `X-ZeroGEX-Schema-Version` HTTP header
and a matching `meta.schema_version` body field (per ADR-0002). Format:
semver `MAJOR.MINOR.PATCH`.

- `MAJOR` — the URL prefix version (`v1` → `1.x.x`, `v2` → `2.x.x`).
  Bumped by ADR only.
- `MINOR` — additive changes: new fields, new sanity-flag codes, new
  warning codes. Bumped in PR title / changelog entry.
- `PATCH` — bug fixes, non-schema behavior changes, spec clarifications.

Consumers who care about compat pin on `MAJOR`; consumers who want the
latest features track `MINOR`. Nothing else needs pinning.

### Why hard-cut, not additive-only

Considered three variants:

**A. Hard-cut to `/v1/` with `/legacy/` 90-day alias.** ← **chosen.**

**B. Additive-only under existing paths.** All new fields opt-in;
existing shape unchanged; consumers pull the envelope by sending a
version header (`Accept-Version: 1`).

**C. Path-level `/v1/` mirror alongside unchanged `/api/`.** Duplicate
every route; new consumers use `/v1/`; old consumers use `/api/`
indefinitely.

Trade-offs:

| | A (chosen) | B (additive) | C (indefinite mirror) |
|---|---|---|---|
| Contract clarity | Excellent — one shape per version | Poor — additive fields defaulted-to-null pollute the schema forever | Good — separate spec per surface |
| Migration cost for customers | Real — 90 days to move | Zero — nothing breaks | Zero — never move |
| Engineering cost | One-time sweep in T2 | Ongoing — every new feature must be defended additively | Doubled maintenance forever |
| Signals commitment | Strong — "we care about the contract" | Weak — "we bolt on and hope" | Neutral |
| Prevents drift recurrence | Yes — the CI gate + spec catches it | No — additive fields silently pile up | Partial — two surfaces to drift |
| Copilot foundation | Solid — one shape to reason about | Fragile — Copilot has to know which fields are safe | Moderate — Copilot picks `/v1/` |

**Choice: A.** The migration cost is real but bounded (90 days is
generous for automated consumers; sophisticated ones will move in
days). Every other property favors A. The signal to customers is
correct: we chose contract clarity over avoiding a migration.

Option B was tempting because it "breaks nothing." But it also fixes
nothing structurally — the ambiguity Johnnie observed *is* the current
shape; keeping it means keeping the ambiguity forever behind a header
flag.

Option C locks us into perpetual double maintenance for zero benefit
beyond the 90-day mark.

### The `/legacy/` alias — mechanics

- Same routes as today, same responses as today (byte-for-byte
  identical), same auth, same rate limits.
- Additional response headers on every `/legacy/` response:
  - `Deprecation: true`
  - `Sunset: <90 days from v1 launch date>` (per ADR-0004)
  - `Link: </v1/{successor-path}>; rel="successor-version"`
- Additional in-body warning (only for consumers who parse JSON):
  the response is unchanged, but the *headers* signal the deprecation.
  In-body warnings would be a breaking shape change; we don't do that
  to `/legacy/`.
- Audit-log-level counter of `/legacy/` hits per key per day, so we can
  monitor migration progress and reach out to any customer still on
  `/legacy/` at day 60.
- After the sunset date: `/legacy/{path}` returns `410 Gone` with
  `Link` header pointing to the successor. No JSON body, minimal
  overhead. Route stays in the codebase for another 12 months as a
  gone-sentinel so we can measure post-sunset access, then removed.

### `/v1/version` — capability & changelog discovery

The single endpoint consumers use to check version, capability
support, feature flags, and changelog. Publicly accessible without a
key (only public metadata).

```
GET /v1/version
```

```json
{
  "data": {
    "schema_version": "1.0.0",
    "build": "bd80bdd",
    "released_at": "2026-08-15T00:00:00Z",
    "endpoints": {
      "count": 108,
      "stable": 89,
      "beta": 12,
      "experimental": 3,
      "deprecated": 4
    },
    "capabilities": {
      "envelope": true,
      "field_status": true,
      "request_id": true,
      "server_processing_ms": true,
      "sanity_flags": true,
      "score_metadata": true,
      "carry_forward": true,
      "market_session_source": ["US_EQUITY", "INDEX", "FUTURES", "CBOE_VIX"]
    },
    "changelog_url": "https://api.zerogex.io/v1/version/changelog",
    "docs_url": "https://docs.zerogex.io/v1"
  },
  "meta": { ... },
  ...
}
```

The `capabilities` block lets a consumer feature-detect on server
version without inferring from behavior. E.g. `if capabilities.field_status`
before parsing responses in `FieldValue` shape (relevant during the
Tier 2 rollout when not every endpoint has been migrated yet).

The `/v1/version/changelog` endpoint returns the machine-readable
changelog defined in ADR-0004.

## OpenAPI 3.1 as source of truth

### What "source of truth" means concretely

- **Spec file:** `openapi/v1.yaml` at repo root, hand-authored,
  reviewed as a first-class artifact in every PR that changes API
  surface.
- **Types:** Pydantic models are *generated* from the spec via
  `datamodel-code-generator` (or equivalent). Handlers reference the
  generated models. Hand-authored Pydantic in `models.py` is preserved
  during the T2 migration (envelope wraps existing models), then
  gradually replaced by generated models in a subsequent tier.
- **Docs:** `zerogex-docs` site (per ADR-0001 decision) consumes the
  spec via Scalar or Redoc. `API_Guide.md` retires.
- **SDK:** future TypeScript / Python SDKs generate from the same spec.
- **CI diff:** every PR runs `openapi-diff` against the base branch;
  breaking changes fail the check.

### Why hand-authored, not auto-generated by FastAPI

Auto-generation is convenient — the current `main.py:280` sets
`openapi_url="/openapi.json"` and FastAPI does the rest. But the
generated spec is a *reflection* of the implementation; it can't
disagree with the code even when the code is wrong. That means:

1. **The spec can never catch bugs in the code**, because the spec
   is the code.
2. **The spec can never be reviewed in a PR** as a design artifact —
   only as a side-effect of the implementation change.
3. **Breaking changes are invisible in review**. A field rename in
   `models.py` is a one-line diff in code and a spec diff nobody sees
   until it lands.

Hand-authored spec inverts all three: the spec is the design; the
implementation is checked against it; CI catches drift.

### CI diff gate

A GitHub Action on every PR:

1. Diffs `openapi/v1.yaml` between `base` and `head` using
   [`openapi-diff`](https://github.com/OpenAPITools/openapi-diff) or
   equivalent.
2. Categorizes changes as `additive`, `patch`, or `breaking`.
3. `additive` — passes; PR title must include `MINOR:` prefix.
4. `patch` — passes; PR title includes `PATCH:` prefix.
5. `breaking` — fails unless the PR has a `breaking-change-acknowledged`
   label AND an ADR link in the description.

The gate is not merely advisory. A PR touching the spec that doesn't
follow the convention doesn't merge.

### Runtime validation

The FastAPI app validates its own responses against the spec in
non-production environments:

- **Dev / CI:** `strict` mode — any response that doesn't match the
  spec raises an exception during the test suite.
- **Staging:** `warn` mode — responses that don't match log a
  warning to a dedicated logger.
- **Production:** `off` — no runtime overhead. If we've done our job
  in dev and CI, prod doesn't need to double-check.

Wired via a middleware that consumes the same spec file.

### Migration path from auto-generated to hand-authored

1. **T1 kickoff:** Export the current auto-generated spec as
   `openapi/v1.yaml`. Manually clean up (remove noise fields, tighten
   descriptions, correct type ambiguities).
2. **T1 spec-first for envelope types:** The new envelope models are
   hand-authored in the spec first; generated Pydantic models are
   used by handlers.
3. **T2 endpoint migration:** Each endpoint's spec entry is hand-authored
   (using the auto-generated baseline as a starting point) before the
   implementation moves to `/v1/`. The envelope wrapper enforces the
   response shape.
4. **T3 onward:** Every new endpoint starts in the spec.

## Semantic versioning policy — full detail

The semver policy for `schema_version`:

### MAJOR (`1.x.x` → `2.x.x`)

Reserved for URL-prefix bumps. Requires an ADR. Triggers a customer
communication campaign per ADR-0004.

Justifiable reasons:
- Cross-cutting envelope shape change that can't be modeled additively.
- Auth model change that isn't backward-compatible.
- Enum removals (e.g. removing a `DataStatus` value).

Not justifiable:
- Adding a new endpoint.
- Adding new optional fields to existing responses.
- Adding new `SanityFlag` codes (they're consumer-tolerant by design).

### MINOR (`1.0.x` → `1.1.x`)

Additive schema changes. Announced in the changelog and PR title
prefix `MINOR:`. No ADR required.

Justifiable:
- New endpoint under `/v1/`.
- New optional field in an existing response.
- New enum value in an open-vocabulary enum (`SanityFlag`, `WarningCode`).
- New optional query parameter.
- New response field with a documented `FieldStatus: not_applicable`
  default for older data.

Not justifiable:
- Any field rename (that's a `MAJOR` unless the rename is on a
  Beta/Experimental endpoint).
- Any type change to an existing field.
- Any change to a required-field constraint.

### PATCH (`1.0.0` → `1.0.1`)

Non-schema changes and bug fixes. Announced in the changelog with PR
title prefix `PATCH:`. No spec change should imply a PATCH bump
alone — usually paired with a code fix.

Justifiable:
- Description tightening in the spec.
- Bug fixes that change behavior back to what the spec already
  specified.
- Performance improvements.

### Stability tiers (per `meta.stability` in ADR-0002)

Stability tiers cross-cut semver:

- **`stable`** — semver policy above applies strictly.
- **`beta`** — MINOR-level changes may include field renames /
  removals. Beta endpoints announce their beta status in the response
  and in docs.
- **`experimental`** — no compat guarantees. May change PATCH-wise.
  Documented explicitly.
- **`deprecated`** — no more changes; only removal at the announced
  sunset date. Emits `Deprecation` + `Sunset` headers.

## The style guide (companion output)

The following naming/format rules become non-negotiable style for
every new `/v1/` endpoint. Enforced by the CI spec-lint step.

### Path conventions

- Kebab-case in path segments: `/v1/gex/by-strike`, not `/v1/gex/byStrike`.
- Nouns for resources: `/v1/gex/summary`, not `/v1/gex/get-summary`.
- Nested paths for sub-resources: `/v1/bots/{bot_id}/trades`.
- Verb prefixes forbidden. Actions on resources go via query
  parameters where possible or (rarely) a POST body.

### Field conventions

- Snake_case in field names: `net_gex_at_spot`, not `netGexAtSpot`.
- Timestamps always suffixed `_ts` (`source_ts`, `calc_ts`, `server_ts`).
- Dates (calendar days) suffixed `_date` (`as_of_date`, `session_date`).
- Durations always suffixed with unit (`age_seconds`, `expected_cadence_seconds`,
  `stale_after_seconds`).
- Monetary values suffixed with unit or context (`price`, `spot_price`,
  `net_gex` — GEX has a well-known unit convention). Documented in
  the field description.
- Percentages as decimals `0.0–1.0` unless the field name is
  `_pct` (which means the value is `0–100`). Consistent across
  endpoints.
- Booleans start with `is_`, `has_`, or use adjective form (`applicable`,
  `synthetic`). Never `flag_*`.

### Query parameter conventions

- Kebab-case in query names: `?window-units=90`, not `?window_units=90`.
  (Path stays kebab; body stays snake; queries kebab — consistent with
  HTTP idiom.)
- Multi-value via comma-separated: `?expirations=2026-08-01,2026-08-08`.
  Not repeated params.
- Booleans: presence-based (`?include-partial`) or `true|false`
  values.

### Symbol conventions

- Uppercase, letters and dots only: `SPY`, `$SPXW.X`. Enforced by regex.
- Symbol normalization is server-side; consumers may send lower-case
  and get back the canonical form in the response.

## Consequences

### Positive

- **Contract is discoverable and version-safe.** A consumer knows
  today what our API looks like a year from now.
- **The `/api/market/vix` failure mode is architecturally impossible.**
  The CI gate catches route removals; ADR-0004's deprecation policy
  handles intentional ones.
- **New engineers ramp on a spec.** No more archaeology through
  `main.py` and 18 router files.
- **Docs and SDKs are automatic** downstream of the spec.
- **Runtime validation** catches shape bugs during development.

### Negative

- **90-day double surface.** Both `/v1/` and `/legacy/` served
  simultaneously. Real cost — extra tests, extra monitoring, extra
  chance for divergence bugs. The gain is worth it; the cost is real.
- **Hand-authored spec is real work.** ~100 endpoints need spec
  entries with reviewed field descriptions, examples, and error
  schemas. Rough estimate: 1 engineer-day per 5 endpoints = ~20
  engineer-days for T2's endpoint sweep.
- **CI wait time grows.** Spec-diff and OpenAPI generation add
  ~30-60s to CI. Amortized against the incident cost of a silent
  breaking change, still a huge net win.
- **Team discipline required.** New endpoints must start in the spec.
  This will be uncomfortable initially and worth defending.

### Neutral

- **Existing FastAPI middleware and infra is preserved.** No runtime
  overhead beyond the (optional) response validation.
- **Existing scope-based auth is preserved verbatim.** Auth is
  orthogonal to versioning.

## Open follow-ups

1. **`/v1/version` public accessibility.** Should this endpoint bypass
   the API key requirement? Recommendation: yes. It's public metadata
   and it needs to be reachable *before* a consumer has a key so they
   can discover what they're integrating with. Decision deferred to
   T1 kickoff but leaning yes.

2. **Rate limit on `/v1/version`.** Public unauthenticated endpoint
   needs a per-IP rate limit. Recommend 60 rpm per IP (generous — this
   is a discovery endpoint, not a hot path).

3. **What happens to `/api/v1/levels/{symbol}` (the one existing
   `/v1/`-prefixed route)?** In the v1 hard-cut it becomes
   `/v1/levels/{symbol}` (drop the redundant `/api/`). `/api/v1/levels`
   remains as a `/legacy/`-style alias for 90 days.
